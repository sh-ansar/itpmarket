# Компании, права и каталоги

## Статус компании

Канонические статусы: `pending`, `approved`, `rejected`, `blocked`.

- `pending` может войти, видеть статус и заполнять настройки;
- только `approved` может запускать сборщики, импорт, отчёты и расписания;
- проверка выполняется в HTTP API и повторно в планировщике;
- старые значения `active`/`setup` читаются как `approved`, `suspended` — как `blocked`.

## Модель доступа

Права формируются из `tenant_roles` + `tenant_role_permissions`, затем применяются
персональные переопределения `tenant_user_permissions`. Доступ к площадке задаётся
на уровне компании в `tenant_marketplace_access`; рабочие данные появляются только
после фактического подключения (`tenant_integrations.status = active`).

Роль, функциональное разрешение и площадка — независимые проверки. Все сотрудники
компании получают один и тот же набор подключённых площадок, а действия различаются
по ролям и функциональным правам.

## Изоляция каталогов

`tenant_catalog_products` — обязательный слой принадлежности карточки компании.
Сырые таблицы существующих сборщиков сохранены, но выдача API пересекает их с
членством текущей компании. Для исходного рабочего пространства действует только
ограниченный migration fallback для старых таблиц без `tenant_id`; другие компании
его не получают.

Характеристики автоматически попадают в:

- `product_attribute_definitions` — нормализованное имя;
- `product_attribute_sources` — исходное имя и площадка;
- `product_attribute_values` — значение конкретного товара;
- `tenant_catalog_filters` — выбор фильтров администратором компании.

Псевдонимы вроде «Сезон» и «Сезонность» объединяются, но исходные названия
сохраняются. Неизвестные характеристики получают стабильный общий ключ, поэтому
модель не привязана к шинам или другой одной категории.

## Ozon.ru Collector

Основные операции Ozon.ru оставлены на прежнем публичном collector-контуре.
`Сбор каталога` запускает `discover` и `enrich-new`, актуализация цен —
`refresh-prices` и `market-search`, полная синхронизация выполняет прежнюю цепочку
из четырёх этапов. Seller API не используется как автоматическая замена этих
операций и не выводится в интерфейсе.

Platform superadmin снова видит исходную карточку `Ozon.ru Collector` с отдельными
списками seller URL и рыночных категорий, ожидаемым продавцом и текущей статистикой
реестра. Настройки продолжают сохраняться в `START_URLS.txt`, `START_URL.txt` и
`EXPECTED_SELLER.txt`, как в рабочем варианте до изменения.

## Карточки площадок и согласование

Единый `marketplace_registry.py` описывает все площадки и их поля подключения.
Каждая компания получает собственную строку `tenant_integrations` для `kaspi`,
`ozon` (Ozon.ru), `ozon_kz`, `halyk_market` и `forte_market`; глобальные поля
конкретного продавца больше не выводятся в настройках компании.

В `tenant_integrations` хранятся только данные конкретной компании:

- `seller_name`, `seller_identifier`, `seller_url`;
- `discovery_status` и безопасный `discovery_json` с источником результата;
- `approval_status`: `draft` → `discovered` → `pending` → `approved`/`rejected`;
- автор и время отправки, проверяющий, время и комментарий решения.

Администратор компании вводит название продавца и, если известно, ID или URL.
Поиск сначала использует явный идентификатор/проверенный домен и уже собранный
локальный каталог. Одно название без доказательства создаёт честный кандидат для
ручной проверки — система не выдаёт такой результат за найденного продавца.
После отправки только platform superadmin может принять или отклонить подключение.
RBAC разрешает площадку пользователю лишь при `approval_status='approved'`.

Для Ozon.kz реализован отдельный marketplace-код, отдельная карточка, продавец,
каталог, права и статусная операция. Отдельный Seller API Ozon.kz не имитируется:
до появления подтверждённой официальной спецификации интерфейс явно показывает
ограничение, а Ozon.ru credentials к нему не применяются.

## Обязательный профиль компании

Название, регистрационный номер/БИН, email и телефон обязательны на регистрации,
при редактировании в кабинете и перед отправкой подключения. Реальные операции
также блокируются, пока профиль старой компании не дополнен. Эти проверки работают
на backend, а не только через HTML `required`.

## Проверка пяти компаний

`tools/five_company_load_test.py` поднимает изолированную временную базу и проверяет
пять компаний с разными площадками и товарными характеристиками. Для каждой он:

1. формирует и согласовывает собственную карточку продавца;
2. загружает собственный каталог и автоматически строит attribute registry;
3. включает свой фильтр;
4. создаёт и завершает собственную операцию;
5. параллельно читает товары и фильтры пятью потоками;
6. проверяет отсутствие пересечения товаров и истории операций.

Запуск: `python tools/five_company_load_test.py --products 150 --rounds 20`.

## Изоляция выполнения сборщиков

При формировании команды сервер повторно загружает пользователя, его компанию и
подтверждённую карточку площадки. В процесс передаются реквизиты именно этой
компании: seller ID для Kaspi, seller name для Halyk Market, внутренний ID для
Forte Market и ссылка на зашифрованные credentials для Ozon.ru. Кандидатный ID
вида `candidate:*` никогда не используется как реальный внешний идентификатор.

Kaspi, Halyk Market и Forte Market после успешного прохода материализуют результат
в `tenant_catalog_products` указанной компании. Исторические общие таблицы служат
только staging-слоем; для всех компаний, кроме исходного legacy workspace, они не
участвуют в пользовательской выдаче. Ozon.ru продолжает использовать прежний
публичный collector и его проверенную схему seller-категорий и рынка.

Контрольный прогон 10.08.2026:

- 29 автоматических тестов — успешно;
- 5 компаний × 150 товаров = 750 изолированных позиций;
- 5 подтверждённых подключений и 5 завершённых операций;
- запись: 316,27 товара/с;
- 300 параллельных групп чтения: 65,71 группы/с;
- проверка пересечений между компаниями: `passed`;
- живой probe публичного Forte Market API: `ok`, категория вернула 11 659 позиций.
